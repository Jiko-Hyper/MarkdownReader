# MDReader 优势导向开发指南

日期：2026-09-27。基线：当前仓库 0.4.0。

本文规定后续产品方向、建议开发顺序和验收方法。所有标为“计划”“目标”的内容均未因本文而交付；阶段名称不是版本或发布日期承诺。现有功能以实际代码、当前 README 和复验结果为准，不沿用旧目录的通过记录证明新功能可用。

## 1. 产品定位

**面向 Windows 用户，让 Markdown 从收到文件、阅读修改到导出交付都更省事。**

最值得打磨的完整流程是：打开一份文档 → 看懂并定位内容 → 请求 AI 修改指定部分 → 核对并应用 → 导出可交付的 Word/PDF。

核心价值应当能用三句话说明：

- 文件在哪里，就在哪里打开和处理；临时查看不要求先整理成资料库。
- AI 改了什么看得清，是否采用由用户决定，采用后能撤销。
- 发给别人之前，能知道导出是否缺图、表格是否完整、哪些内容会降级。

免费、本地保存、主题、多标签不是独有卖点。没有同机实测，不宣传“更快、更轻”；没有实物核验，不宣传“无损转换”“完美兼容”。

## 2. 优先服务谁

| 用户与场景 | 要解决的具体问题 | 成功的表现 |
| --- | --- | --- |
| 经常接收 AI 生成稿的人 | Markdown 不便阅读，修改后还要交 Word/PDF | 收到文件后能独立完成查看、修改和交付 |
| 学生、教师和一般办公用户 | 报告有标题、表格、图片，导出后需要大量修版 | 常见报告无需大量返工即可交付 |
| 开发者及项目参与者 | 项目说明散落在不同文件夹，需要快速查看和小改 | 直接打开原文件，不破坏路径、编码和附件 |

首批试用优先前两类；第三类提供技术文档兼容样本。重度知识库、复杂论文排版、扫描件识别不是首轮主目标。

## 3. 已有基础与真正需要补齐的地方

| 方向 | 0.4.0 已有基础 | 下一步增量 |
| --- | --- | --- |
| 文件阅读 | 拖入原文件、多标签、查找、目录、阅读位置、三种主题 | 检查真实长文的定位稳定性，降低设置与操作成本 |
| AI 协作 | 当前文档上下文、差异预览、手动应用、撤销、过期结果校验 | 选区修改、局部采纳、更清楚的影响范围 |
| 文档交付 | Word/PDF 导出、统一快照与预检、后台任务 | 固定语料的版式质量、少量实用样式、导出后核验 |
| 格式转换 | PDF/DOCX → Markdown、Markdown ↔ HTML | 结果与降级报告联动，转换后便于核对和继续编辑 |
| 数据保护 | 保存冲突检测、恢复快照、删除进回收站 | 每次新增操作继续遵守现有保护，不另建写入通道 |

当前已知边界必须继续对用户可见：Windows 10/11 x64；单篇打开上限 8 MB；有限 TeX 子集；脚注与 Mermaid 不是完整渲染；PDF 转换无 OCR；复杂版式可能降级。格式转换插件和普通阅读/导出的支持范围不同，不能混用一张“支持列表”。

## 4. 阶段 A：先让完整流程可靠

目标：让真实用户走通“打开 → 修改 → 导出”，找出最妨碍交付的三项问题。此阶段通过后再扩大功能。

### A01：建立可重复的交付样本集

计划收集至少 20 份经授权、脱敏或自行制作的文档，覆盖普通报告、长文、中文与英文混排、多级列表、跨页表格、宽表格、本地图片、长代码、公式及缺失附件。每类记录输入、预期结构、已知降级和目标输出。

验收：

- 普通段落、标题、列表、表格单元格和代码的内容不静默丢失；文本抽取比较允许换行等排版差异。
- Word 中常见正文和表格保持可编辑；公式图片等降级明确记录。
- PDF 逐页查看无截字、图片拉伸、表格裁列、代码越界；长表格检查跨页表头。
- 缺图、失败、取消、同名目标和未保存编辑都有真实操作记录；失败不能破坏原文或已有产物。
- 所有不支持的样本都有可见说明，不将其计入“成功保真”样本。

交付物：样本清单、可重复检查、逐页视觉验收记录、按严重度排序的问题列表。先复用现有渲染和导出测试，增加确实能捕获内容或版式错误的用例。

### A02：缩短首次使用路径

当前状态（2026-09-27）：待验收。桌面导出入口、对应随包插件安装/启用引导、完成后打开产物或所在文件夹已实现；真人 5 人观察尚未开展，不将程序测试视为首次独立完成率。开发范围、验证记录和试用表见 [A02 首次使用流程](A02_FIRST_USE.md)。

计划将“打开文件”“让 AI 修改”“导出 Word/PDF”作为最容易找到的主要入口。先观察现有布局，再做最小调整；不因本指南重做整套界面。

验收：

- 5 名首次接触的试用者中，至少 4 名无需口头指导完成打开、查找、手工修改和导出；这是试用目标，不是现有成绩。
- 没有配置 AI 时仍能完成阅读、编辑和离线导出。
- 缺少或停用导出插件时，操作入口能指向对应随包插件，而不是只报错。
- 完成后能直接打开导出文件或所在文件夹；操作作用于哪篇文档始终明确。

### A03：修复阅读和编辑中的位置丢失

针对真实复现的问题检查切标签、切主题、字号变化、源码与预览跳转。只有现有实现不达标时才新增代码。

验收：原来正在阅读的段落仍在附近；选区定位不跳到另一个同文段落；文档 A 的光标、未保存内容和撤销记录不被文档 B 干扰。中文输入法组合期间切换也要实测。

阶段 A 出口：20 份样本有完整结论；内容丢失或错误覆盖问题为零；至少一轮首次使用观察完成，核心流程阻断项已修复。

## 5. 阶段 B：把 AI 局部修改做成主要特色

### B01：选中哪里，修改哪里

计划增加选区操作入口，首批只提供润色、精简、扩写和自定义要求。已有整篇修改继续保留。

用户流程：选中文字 → 选择修改意图 → 查看原文与建议 → 应用或取消。

实现约束与验收：

- 请求保存文档身份、内容版本和准确选区，不能用“全文替换第一个相同字符串”定位。
- 默认只发送选区；若需要周边或全文上下文，先清楚显示范围，由用户选择。
- 应用只改变目标范围，其他文字保持原样；重复段落、中文、表情、跨行选区都需验证。
- 等待期间正文变化、切换到其他文档或文档关闭时，禁止旧结果直接覆盖；引导返回原文或重新生成。
- 一次应用对应一次撤销，取消不改变正文，应用不自动保存。
- 超时、格式错误、截断回复和空结果不能成为可应用的新正文。

### B02：按修改块逐项采纳

在 B01 稳定后，计划将整篇建议拆为可读的修改块，提供“采用此处”“保留原文”和“全部采用”。

首版只处理能可靠定位且互不重叠的修改块；发生依赖或重叠时合并展示或要求重新生成，不猜测应用位置。每次采纳后更新剩余块的版本与定位，防止后续块写错位置。

验收：只采纳第二处时，第一处和第三处不变；撤销后内容与修改状态一致；大量改动时仍可浏览；代码、链接目标、表格和数字的变化能在差异中辨认。差异准确不等于 AI 内容正确，界面仍保留核对步骤。

### B03：失败之后可以继续工作

计划保留未发送问题和失败输入，提供明确的重试或重新生成入口。沿用现有不自动重复收费请求的原则；不把远端已收到请求误报为已撤销。

聊天持久化暂列候选，只有试用证明关闭窗口丢对话是高频阻碍时再做；届时提供显式启用、清除记录和保存范围说明。

阶段 B 出口：选区修改及异常分支回归通过；试用者能解释 AI 改了哪里、拒绝一处并撤销一处；保留已有整篇修改流程。

## 6. 阶段 C：让交付质量成为长期优势

### C01：两套实用导出样式

计划先提供“简洁报告”和“技术文档”两套样式，控制标题层级、正文、表格、代码和图片，不先制作复杂模板商城。

验收：相同输入重复导出有稳定的版式；阅读主题不影响打印配色；中文字体缺失时有替代提示；Word 重开后结构不变；PDF 在第二个阅读器中检查可读性。Word 和 PDF 分别验收，不承诺像素级一致。

### C02：导出预检能带用户回到问题位置

沿用现有统一预检，计划把缺图、过宽表格、不支持公式等提示关联到原文位置，给出具体处理建议。阻止项与提示项保持明确；已有缺图阻止规则不因方便导出而静默放宽。

首版优先做好问题定位和代表性页面预览；若预览来自不同渲染器，明确它不是最终 PDF 页面的保证。最终分页预览只有基于实际产物才能标作最终效果。

### C03：转换完成后方便核对

计划让转换任务显示结果路径、附件目录和降级摘要，支持直接打开生成的 Markdown。首版继续读取磁盘文件，遇到未保存内容给出明确提示，不暗中混用编辑缓冲。

验收：转换不覆盖源文件；缺失图片、无文字 PDF 页和不支持结构有说明；附件移动要求清楚；失败不留下被当成成功结果的半成品。PDF 转换以可编辑内容提取为目标，不宣传恢复原版式。

### C04：公式与图表按需求补齐

先统计样本集中最常失败的公式，再决定扩展解析范围或替换渲染方案。可编辑 Word 公式先用固定样本验证，验证通过后才进入正式插件；不支持时保留表达式和明确降级。

Mermaid 仅在核心用户反复遇到阻断时进入排期。引入任何新依赖前核查离线运行、许可证、安装包增长及桌面/网页/导出的一致性。

阶段 C 出口：两套样式通过固定语料验收；主要降级可定位；试用中的导出返工原因与次数比阶段 A 基线减少。没有同样本数据，不宣称质量提升比例。

## 7. 技术落点与实现规则

路径均相对于当前 `MarkdownReader/` 根目录。旧文档中的 `build/main.py`、`scripts/` 等路径不能直接复制到新任务。

| 能力 | 优先复用的现有模块 | 必须保持的边界 |
| --- | --- | --- |
| AI 请求与界面 | `mdreader/ai_providers.py`、`ai_assistant_ui.py`、`webui/` | 请求执行、修改校验和控件交互分层；密钥不进入日志 |
| 文档修改与恢复 | `documents.py`、`document_ui.py`、`recovery.py` | 保留冲突检测、未保存状态和按文档隔离的撤销 |
| 阅读定位与搜索 | `navigation.py`、`find_ui.py`、`winui.py`、`render.py` | 不用重建编辑缓冲解决显示问题 |
| 导出 | `exporting.py`、`plugin_tasks.py`、`plugins/official/` | 快照、预检和提交由宿主管理；插件生成临时产物 |
| 格式转换 | `conversion.py`、`plugins/official/document-convert/` | 原文件只读、目标独占创建、附件与结果一起处理 |
| 插件分发 | `plugins.py`、`plugin_trust.json`、`tools/` | 插件版本、依赖、受信清单和发布包一起验证 |

遵守以下开发规则：

1. 桌面与网页的同一业务规则共用核心实现；若首版只提供桌面入口，使用说明明确范围。
2. 新功能先交付一个完整用户流程，再扩充按钮和选项；避免在 `winui.py` 中继续堆入独立业务逻辑。
3. 网络、转换和导出任务不阻塞主界面；失败、取消、关闭文档和结果过期都属于功能的一部分。
4. 数据格式变化提供向后兼容或迁移说明。普通 Markdown 仍可脱离软件使用。
5. 外部 AI 控制与内置模型对话保持权限和密钥分离；文档中的指令不能自行扩大上传或写入范围。
6. 不为路线规划重写框架。只有真实阻碍与对比实验能证明收益时，才评估更换编辑或渲染组件。

## 8. 每项任务的开发与发布流程

开工前写清：用户场景、现状问题、最小交付、暂不包含的范围、涉及模块、验收样本、失败分支。先核实已有实现，避免重复开发。

开发时先跑受影响的针对性检查；发布前在当前仓库根目录运行统一检查：

```powershell
powershell -ExecutionPolicy Bypass -File tools/scripts/check.ps1
```

AI 变更重点检查 `tests/test_ai_providers.py` 及相关界面；导出和转换重点检查 `test_exporting.py`、`test_conversion.py`、`test_official_plugins.py`；编辑与定位重点检查 `test_document_ui.py`、`test_navigation.py`、`test_native_tabs.py`、`test_ime.py`。需要新回归时按实际行为增加，不以函数是否被调用代替用户结果。

发布必须另做真实窗口和发布包验证：中文输入法、三种主题、100%/150%/200% 缩放，干净机器无系统 Python 的启动与离线导出，以及保留旧数据的升级。无相应环境时记录未验证，不能写成通过。

修改只涉及文档时检查链接、路径、计划与已完成状态的一致性，无需启动全套应用测试。

发布阻断条件：内容丢失、错误覆盖、修改应用到错误文档、核心任务无法完成、产物缺失内容却被报告成功。样式小问题可明确记录后安排修复，但不能掩盖内容问题。

## 9. 怎么衡量方向是否有效

先建立阶段 A 基线，再设改进幅度；以下是建议采集口径，不是现有成绩。

| 指标 | 采集方式 | 用途 |
| --- | --- | --- |
| 首次独立完成率 | 固定任务、相同引导条件，记录成功人数/总人数 | 判断是否容易上手 |
| 打开到完成交付的时间 | 同一组文档、同一任务，记录中位数与最慢情况 | 判断流程是否缩短 |
| 导出返工 | 记录是否返工、耗时、原因和受影响格式 | 决定优先修哪类版式 |
| AI 修改可控性 | 观察定位、拒绝、采纳、撤销能否完成 | 判断用户是否能掌控结果 |
| 数据与内容错误 | 按严重度登记每个可复现案例 | 任何丢失或错误覆盖立即插队 |
| 交互响应 | 固定电脑、文档和标签数记录延迟与内存 | 防止新功能拖慢日常操作 |

性能测量将本地处理时间与模型服务等待时间分开。首批建议邀请 5–10 人试用一周，正文与日志由用户主动提供并脱敏，不默认采集文档内容。小样本反馈用于发现问题，不外推为全体用户偏好。

## 10. 暂缓事项与重新考虑的条件

| 暂缓事项 | 原因 | 重新考虑条件 |
| --- | --- | --- |
| 完整知识图谱、数据库式笔记管理 | 对当前交付流程帮助有限，维护面大 | 核心用户重复出现跨文档组织阻碍 |
| 手机端、云同步、多人实时编辑 | 需要独立的平台和数据一致性投入 | 桌面流程稳定，跨设备需求成为主要流失原因 |
| 全量所见即所得编辑器重写 | 容易影响输入法、撤销与格式保真 | 轻量定位和局部编辑仍不能解决反复出现的写作问题 |
| 自主执行命令的 AI 代理 | 超出当前文档助手范围 | 有明确、受控且可验证的用户任务 |
| OCR、复杂论文排版、模板商城 | 分散首轮质量投入 | 有足够真实样本和持续使用需求 |

暂缓不代表永远不做。任何候选功能都先回答：它减少了当前用户的哪一步、解决了多少重复问题、增加多少维护成本、怎样证明有效。

## 11. 下一轮可以直接领取的任务

建议单轮只承诺以下三项，按顺序推进：

1. **A01：固定样本与现状报告。** 整理 20 份样本，实际生成 Word/PDF，形成缺陷优先级；先修复发现的内容和文件安全问题。
2. **A02：首次使用走查。** 用实际测试版观察 5 名新用户完成任务，修复前三个核心阻碍，不先重做 UI。
3. **B01：选区 AI 修改。** 在基础问题收敛后，实现选区请求、差异核对、版本校验和一次撤销，完成桌面真实窗口验收。
