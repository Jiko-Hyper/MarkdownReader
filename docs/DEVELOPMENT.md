# 开发流程

## 1. 环境与启动

基准环境：Windows、Python 3.12、tkinter；Node.js 用于网页逻辑测试，无 npm 依赖。先使用标准库内置 Markdown 引擎完成验证，增强引擎另做兼容验证。不要从不明来源下载 WebView2 DLL。

在仓库根目录执行：

```powershell
python build/main.py --workspace .dev-workspace
python build/main.py --browser --workspace .dev-workspace
```

开发数据与真实笔记分开。首次启动会创建开发工作区；不需要迁移旧笔记。当前目录尚未初始化 Git，可由维护者决定仓库与远端；提交前检查差异，禁止提交个人笔记、缓存和分发产物。

## 2. 一次功能变更

1. 写清用户操作、预期结果、涉及模块和验收标准。
2. 在现有层级内实现最小完整功能；涉及文件格式或 API 的变更先说明兼容方式。
3. 修复数据丢失、路径、安全或并发问题时增加能重现问题的回归测试。
4. 运行统一检查，再对涉及的界面操作做手动验收。
5. 更新使用说明、迭代记录，记录测试结果及尚未覆盖的情况。

## 3. 自动验证

```powershell
powershell -ExecutionPolicy Bypass -File scripts/check.ps1
```

依次验证：文件写入失败恢复、路径边界、回收站失败、服务隔离；内容指纹与冲突写入、编码/换行保真、恢复快照；内容白名单；两套引擎的 Markdown 保真对比；导入/导出与重复目标确认；当前环境引擎与强制内置引擎的 HTTP 全流程冒烟；JavaScript 语法与保存/查找/目录状态；启动版本入口。任一失败会终止流程并返回失败状态。

结束时只清理本次运行产生的临时目录（`python/`、`mdreader-smoke-*`、`mdreader-selftest`），不会整目录清空 `.testtmp`——那里可能还有别人正在用的复验会话数据。

所有自动化数据都在独立临时目录。`MDREADER_TEST_HOME` 如设置，只作为临时目录的父目录，绝不清空它。符号链接测试在缺少 Windows 权限时会标为跳过，需要在有开发者模式的机器补验。

### 3.1 性能基线

`开发框架.md` 7.2 要求先建立基线而不是先做优化。可重复执行：

```powershell
python scripts/bench.py --docs 1000 --long-mb 1 --big-mb 7.5
```

脚本在临时目录里生成约 1,000 篇普通文档、一篇 1 MB 长文和一篇 7.5 MB 大文档，测完即删。

2026-09-25 记录（AMD Ryzen 9 8945HX / 32 逻辑核 / 31 GB / Python 3.12.9 / markdown-it-py / Windows）：

| 操作 | 耗时 |
| --- | --- |
| 扫描项目（1,003 篇，9.6 MB） | 24 ms |
| 搜索常见词（60 条命中） | 58 ms |
| 搜索无结果（需读完全部文档） | 143 ms |
| 渲染普通文档 | 3 ms |
| 渲染 1 MB 长文 | 1.5 s |
| 渲染 7.5 MB 大文档 | 2.3 s |
| 导出整本（1,002 篇） | 7.1 s |

结论：常规文档（KB 级）与资料库检索都在毫秒级，暂不需要索引系统；**MB 级单篇文档的渲染是 1–2 秒量级**，属于已知特征（markdown-it 排版 + 内容白名单遍历），出现明显卡顿再针对性优化。重复标题的锚点生成曾是平方复杂度，已改为按基名计数（1 MB 长文从 2.7 s 降到 1.5 s）。

### 3.2 多标签编辑的开销（0.2.8 / E01）

E01 变成“每份文档一个编辑控件”后，凡是要遍历控件的操作都要重新量一遍，否则开着十几个标签时输入会变卡。测量方法：开 20 份文档（每份约 4 KB），逐个切到源码，然后对同一操作计时；对照组是 `build/dist/MDReader-0.2.7`（单控件架构）跑同一脚本。

| 操作（20 个标签） | 0.2.7 单控件 | 0.2.8 每文档一控件（急切重排） | 0.2.8（惰性重排，当前） |
| --- | --- | --- | --- |
| Ctrl+滚轮缩放一次 | 16.1 ms | **202.5 ms** | **13.5 ms** |
| 切换一次主题 | 75.8 ms | 284.4 ms | 73.6 ms |
| 源码 ↔ 预览切换一次 | 5.1 ms | 5.1 ms | 2.4 ms |

结论：**必须惰性重排**——一次 `configure_tags` 是约 40 次 `tag_configure`，乘上标签数后会随标签线性增长。现在 `apply_theme`/`on_zoom` 只重排屏幕上的控件，隐藏控件标记为过期、由 `_show()` 在回到该标签时补上（`tests/test_native_tabs.py::test_hidden_editors_are_restyled_only_when_they_come_back` 锁住该行为，并已用“装回急切重排”的方式验证该用例确实会失败）。剩余的约 14 ms / 74 ms 与 0.2.7 持平，来自 ttk 样式、标签栏重建与内嵌预览重绘，不是 E01 引入的。

内存（同一脚本，psutil 读 RSS）：20 份文档从 48.3 MB 增到 50.2 MB（+1.9 MB），再把每个标签都切到源码后为 51.7 MB（+1.5 MB，编辑控件持有正文）。关闭标签即释放（对应用例断言控件与适配项数量回落）。这是“记录内存变化”，不是零增长承诺。

### 3.3 测量中发现的既有问题（0.2.8 记录，未修）

同一套方法在测多标签开销时量到两处**0.2.7 就存在**的行为，本轮不改（保持一次迭代一个主要问题、便于判断来源），只记录并排期：

| 现象 | 0.2.7 | 0.2.8 | 说明 |
| --- | --- | --- | --- |
| 预览（阅读）状态下换主题，正文跳回顶部 | 0.5001 → -0.0926 | 0.5001 → 0.0480 | 共用预览控件在换主题后重排，`yview_moveto(旧位置)` 落在内容重建之前。属 B06「阅读位置」范围，用户可见（读长文时换主题会丢位置）。测试用 `test_each_tab_keeps_a_nearby_reading_position_in_preview` 锁住“切标签回到附近段落”，但不锁换主题这一条。 |
| 预览模式下切到**另一份**文档要整篇重排 | 每次 0.42 s（1.4 MB） | 每次 0.42 s（1.4 MB） | E01 规格明确“每个标签持有独立源码编辑控件、预览单独展示”，共用一份预览就必须重排；属既有「MB 级渲染 1–2 秒」限制的一部分。若要消掉需“每标签预览缓存”，代价是内存随打开文档数增长，列入候选。 |

结论：多标签本身的开销已与 0.2.7 持平（见 §3.2），上表两项是共用预览控件与既有重排时序带来的，不是每文档一编辑控件引入的回归。

### 3.4 测试不得自己满足被测前提（0.2.8 白框回归的教训）

E01 的人工验收发现 Windows 白色组合框回来了：`InlineIME.editable` 默认 `False`，而 `handle_message` 在不可编辑时原样转发 `WM_IME_SETCONTEXT`（不剥掉 `ISC_SHOWUICOMPOSITIONWINDOW`），于是系统画回自己的白框。生产代码忘了把编辑控件设为可组合——**而所有相关用例都先自己调了 `set_editable(True)`**，把这个前提满足了，所以自动化全绿却漏掉了这个用户可见的缺陷。

由此确立两条硬规则：

1. **用例只断言结果，不代设前提**：涉及输入法组合的测试与验收脚本一律去掉 `set_editable(True)` 这类“帮忙”，改为断言正常流程之后该状态已经是期望值（`tests/test_native_tabs.py::test_every_tab_editor_is_composition_ready_without_manual_setup`、`scripts/acceptance.py`【输入】小节）。只有确实无法在无头环境复现的外部条件（如窗口焦点）才允许用生产代码里的处理函数模拟（`win.ime._focus_in()`），并在注释里写明模拟的是哪一环、被测的又是哪一环。
2. **改架构时先问“这个前提以前是谁设置的”**：删掉一条加载路径（这里是 `_set_widget` 里的 `set_editable(True)`）时，要顺带确认它顺手做过的所有副作用都有了新的归属。可编辑性最终收敛到 `winui.py::_show()` 一处，因为“屏幕上是谁”才是它的真正依据。

### 3.5 升级安装副本必须检查程序是否在运行

`scripts/update-installed.ps1` 先对每个目标文件做一次独占打开探测。Windows 会把活动进程加载的 `native_bridge.dll` 一直映射着，脚本又是“先整体备份、再逐文件拷贝并校验哈希”，一旦中途遇到被占用的文件就会中断，留下**半更新**的安装副本——部分模块新、部分模块旧，随后安装副本验收会以与改动无关的原因失败（本次就出现过一次 63 通过 5 失败的无效记录）。

现在的判定分两种：

- 被占用、但**内容与源码已经一致**（哈希相同）→ 安全跳过并打印 `Skipped (locked but already identical)`。没什么可拷的，跳过不会造成半更新，也不必打扰正在使用程序的人。
- 被占用、且**内容与源码不同** → 拒绝执行并提示先关闭程序；不要为了“更新成功”去结束别人的进程。

更新完成后仍要核对三处哈希，并重新生成安装副本验收记录；旧的失败记录要显式标为无效或直接覆盖，不能让一份半更新状态下的记录留在 `docs/` 里当结论。

### 3.6 反向验证与整套检查不能同时跑（0.2.8 / F01 的教训）

反向验证的做法是**临时把源码改回旧行为**、跑目标用例、看它是否失败，再改回来。这类脚本会在运行期间**真的改写 `build/` 下的文件**，所以：

- 反向验证脚本与 `scripts/check.ps1`、验收矩阵**绝不并发**。一次并发就出现了 3 项与改动无关的失败（源码正被改回旧行为的瞬间被别的进程导入）。
- 每次反向验证都要在 `finally` 里恢复原文件，并在恢复后再跑一遍目标用例确认回到绿；只看到“失败符合预期”就收工，容易把旧行为留在工作区里。
- 反向验证结论要写清**改了什么、哪几项失败**，而不是只写“已验证会失败”；对已被证伪的断言，还要确认失败原因确实是那条断言，而不是脚本自身报错。
- **验收脚本本身也依赖内部细节**：F01 的【文件夹】小节原先把窗口的“签名”字段清空来模拟“轮询间隔已过”，后来界面改成“后台线程置脏标记、主线程读标记”，该字段就不再被读取，脚本于是一次真失败（安装副本 89/1）。所以验收脚本必须跟着**接口语义**走（这里改为置脏标记 + 清管理器缓存），每次改完界面都要重跑一遍矩阵，不能因为“上次是绿的”就跳过。

#### F01/F02 已落地的工程约定（2026-09-25）

- **删除类功能必须“失败即拒绝”**：回收站不可用时只保留文件并说明原因，绝不在同一分支里补一次 `os.remove`；即使回收站 API 报成功，也要复查文件是否真的不在磁盘上（`remove_doc` 的两道检查）。对应用例把“回收站失败改成永久删除”装回去必须失败。
- **“先另存再删除”必须另存到别处**：写回即将被删除的原文件，等于让用户以为保住了修改，实际随原文件一起进回收站。工作区文档用 `save_doc`，原文件夹文档必须用 `save_as`。
- **已删除的文档不得被保存悄悄建回**：`cur_loose["deleted"]` 一旦为真，`save_loose` 直接转「另存为」并给出提示；否则 `write_checked(..., 'missing')` 会把原路径重新创建出来。
- **测试里的假回收站要真的把文件移走**：只 `return True` 的 mock 会掩盖“文件其实没被移动”的实现缺陷（本轮就是这样先骗过了自己一回）。统一用 `fake_recycle()`（`os.remove` + 返回 True）。
- **真实系统对话框必须被 mock 掉**：桌面删除会弹 `askyesnocancel`/`askyesno`，漏掉任一个就会让用例挂在真实弹窗上（表现为整套测试卡住，而不是失败）。

### 3.7 后台线程不得触碰界面控件（F01 的教训）

文件夹监听在后台线程里跑，最初它发现变化后直接调用窗口的刷新方法。这在结构上就是错的：Tk 的 `after` / `configure` 只在主线程安全，窗口关闭后还会继续报错；实测还让整套测试的耗时在 47 秒与 206 秒之间抖动。

现在的约定是**后台线程只置标记，界面在主线程的轮询里读标记**：`TreeWatcher` 的回调 `_mark_folders_dirty()` 只写一个布尔值，`folder_watch_tick()`（由 `after` 驱动）看到标记才刷新。用例 `test_the_watcher_only_signals_and_never_touches_widgets` 直接锁住这条边界，把“界面不读脏标记”装回去会失败。

### 3.8 子进程的文本输出必须显式定编码（0.2.8 / F01 的教训）

系统选择框由 `powershell.exe` 弹出，选中的路径靠**被重定向的标准输出**回传。Windows PowerShell 5.1 在这种情况下按本机 ANSI 代码页写字节（中文系统是 GBK），核心却一律 `decode("utf-8", "replace")`；`C:\Users\简\Desktop\笔记` 于是变成一串 `U+FFFD`，程序拿着磁盘上不可能存在的路径去查 `os.path.exists`，回给用户的是「无法打开这个文件夹：找不到文件夹：…」。这类失败有欺骗性：现象像权限或路径问题，根因是编码，而且**只有真实外壳在场时才出现**——所有界面用例都把 `_dialog_folder` mock 掉了。

现在的约定：① 让子进程**显式按 UTF-8 输出**：脚本前统一加 BOM-less UTF-8 前言（`[Console]::OutputEncoding` + `$OutputEncoding`），并用 `try/catch` 包住，旧外壳拒绝该开关时仍能继续；② 解码侧**先 UTF-8 严格解码，失败再退到本机代码页**（`mbcs`），绝不用 `errors="replace"` 把信息抹成 `U+FFFD`；③ 回归用例必须**真的起一次外壳**跑完「回传 → 解码 → 使用」整条链（`tests/test_folders.py` 的 `FolderDialogRoundTripTests` 把 `_dialog_folder` 换成真实 `_run_ps`），验收矩阵也加了同一件事的【对话框】小节。这与 §3.4 的白框是同一类盲区：**被测前提在测试里被自己替换掉了**。

### 3.9 没有 BOM 的 PowerShell 脚本只能写 ASCII（P01 的教训）`scripts/update-installed.ps1` 由编辑器保存为**不带 BOM 的 UTF-8**。Windows PowerShell 5.1 读这种文件时按本机 ANSI 代码页解释，于是新加的两行中文注释被解成了乱码，其中一半个字节恰好凑成引号，把后面的 `foreach` 块整段吞进字符串——脚本**不报错、正常退出、打印「已更新」**，但 `mdreader/`、`webui/` 一个文件都没同步。发现方式是核对同步后两边的 SHA256：安装副本里根本没有新模块。

约定：**这个脚本里只能写 ASCII**（`build/build_dist.ps1` 之所以能写中文，是因为它带 UTF-8 BOM）。更一般地说，凡是**由 PowerShell 自己解释**的脚本（`-File` 运行的 `.ps1`），要么带 BOM，要么保持 ASCII；把中文放进 `python -c` 或用 Python 写文件都不受这条约束。同步安装副本后**必须核对哈希**，不能只看脚本打印的「Updated」——这正是本项目的反向验证习惯：结果证据要独立于执行者的自述。

### 3.10 阅读时的滚动与缩放开销（按文档规模测量）

试用反馈是「文章上下翻动、字体放大缩小卡顿」。§3.2 只量过“开 20 个标签时一次缩放”的总量（每份文档 4 KB），**没有量过单篇长文本身**——而这次的问题是随正文规模增长的。

测量方法：`scripts/bench_interaction.py` 已按这个口径重写（0.2.8 的旧版只测 180 KB 文档，报出的 19 ms 看不见问题）：

```powershell
python scripts/bench_interaction.py --mb 0.2,1.0 --rounds 3
```

它生成 0.2 MB 与 1 MB 两篇长文，先测缩放（新开文档上先缩放，让两个规模的“首次全量排版”都在同一处发生），再按人类节奏喂滚轮，最后换主题。对照组是**改前那版 `winui.py` 的还原副本**跑同一个脚本：本轮没有版本历史，副本是对着色后的当前文件逐处还原出来的，只用于对照、不进仓库。下表是同一台机器上新旧各 1–2 轮的读数，取中位数：

| 操作 | 文档 | 改前 | 改后 |
| --- | --- | --- | --- |
| 一次 Ctrl+滚轮（含 Tk 重排） | 0.2 MB | 347 ms | **118 ms** |
| 一次 Ctrl+滚轮（含 Tk 重排） | 1 MB | **3702 ms** | **76 ms** |
| 一次六格缩放手势（整个过程） | 0.2 MB | 1503 ms | **401 ms** |
| 一次六格缩放手势（整个过程） | 1 MB | **21753 ms** | **361 ms** |
| 滚轮一格（事件处理） | 0.2 MB | 11.8 ms | **0.22 ms** |
| 滚轮一格（事件处理） | 1 MB | 13.1 ms | **0.20 ms** |
| 十格滚轮手势的事件处理合计 | 0.2 MB | 116.6 ms | **4.5 ms** |
| 十格滚轮手势的事件处理合计 | 1 MB | 126.9 ms | **10.8 ms** |
| 预览下切一次主题 | 0.2 MB | 978 ms | **478 ms** |
| 预览下切一次主题 | 1 MB | 10414 ms | **2311 ms** |

两点读法：① 改前的缩放耗时基本**不随文本长度增加**（0.2 MB 347 ms 对 1 MB 3702 ms 的差别来自链接总数），说明瓶颈是每链接的固定开销；改后 0.2 MB 反而略高于 1 MB，属 Tk 排版与计时噪声，两版都落在同一量级。② 滚轮“一格事件”变快不代表滚得更少：十格手势两版都前进 12–13 行，只是把重复的视口重绘合并了。

改前的缩放耗时是**随链接数量**而不是文本长度增长的：`ensure_link_tags()` 每次都对全文每一个链接标签重新 `tag_bind` 三条 Tcl 命令（点击/进入/离开），1 MB 基准文档里有 3768 处链接（改前就是 3768 个标签），单次缩放因此有 1.1 万次 `tag_bind`；profile 显示两次缩放的 Tcl 调用合计约 4.9 s 全花在这一处。逐项修法：

1. **一个目标一个链接标签**（`_link_tag`）：按 URL 去重后，重复出现的同一链接共用标签、颜色、光标与打开动作；随之 `ensure_link_tags()` 用调色板身份与标签数做判据，只处理新增标签。
2. **字面量与标签方案只算一次**（`_font` 记忆化、`_tag_plan`）：一次重排原本要创建约 170 个 `tkfont.Font` 并重复遍历全部代码块标签，现在同一组字号/字重只解析一次；`configure_tags` 按“主题项 / 字号项”分开，缩放只重发带字面的那一半，Tk 对未变化的标签选项直接短路。
3. **缩放只重排屏幕上的控件**：`_refresh_imes(widget)` 不再遍历所有编辑控件；`_apply_zoom` 只在正文真的因为换行而移动了首行时才 `yview(anchor)`——`yview` 本身会强制一次全量排版，是单次缩放最贵的一步。`base_size` 是“瞄准的目标”，实际重排每个 32 ms 窗口最多一次。
4. **滚轮按帧合并**（`ScrollCoalescer`）：滚轮消息先累计、8 ms 后统一位移一次（`yview_scroll(..., "pixels")`），一格 40 像素的换算与 Tk 自带绑定逐位一致（`units()` 用截断而不是四舍五入，否则向下一格会变成 41 像素）。用户看到的位置不变，但快速拨轮不再积压。

回归用例：`tests/test_reading_performance.py` 锁的是**工作量与行为**而不是墙钟时间（墙钟在 CI 上会抖）：一个目标只建一个标签、缩放不再重绑全部链接、换主题每个链接只处理一次、滚轮像素换算与 Tk 一致、一串滚轮只位移一次且真的滚动了视口。表内嵌表格只在调色板或字号真的变化时才重排自己的标签网格（`_table_style`）。

已知未修（不在本轮范围）：① 预览模式下换主题仍会重建整篇正文（1 MB 约 2.3 s，来自 §3.3 记录的 B06「阅读位置」那条），真正的修法是缓存渲染结果或避免整篇重排；② 预览里点链接在**重新渲染或换主题之后**不再触发——这一条改前改后一致（两边都是首次渲染可点、重排后不可点），是既有的既有缺陷，本轮不混进来。

### 3.11 反向验证还原文件必须按字节写回（2026-09-25 的教训）

反向验证的脚本常常这样写：先把原文件读进内存、改一处、跑用例、再把原内容写回去。用
`Path.read_text()` / `write_text()` 做这件事在 Windows 上会**静默改变文件**：读取时把 `\r\n` 统一成 `\n`，
写回时又把 `\n` 翻成 `\r\n`。于是“还原后 SHA256 一致”这条自检会失败——而失败的原因不是被测代码，
是脚本自己改了文件；同一份源码换个换行风格还会连带改变**插件包的哈希**（包内就是这些字节），让受信清单
跟着变。本仓库的文本文件统一用 LF：还原一律 `read_bytes()` / `write_bytes()`，并且**在还原后重新打包、
再核对一次受信清单**，才发现得了这类“看起来还原了”的假象。

### 3.12 反向验证必须先从原始副本还原再取基线（2026-09-26 的教训）

反向验证脚本被**中途杀掉**时（本轮是一个用例走到了真实的模态对话框上，一直等不到人点），它改回旧行为的那一处就留在了工作区里。更糟的是第二轮脚本启动时直接读当前文件当基线——**基线取自一棵已经被改过的树**，于是整轮对比都拿错误状态当正确答案，结论全部不可信。发现方式是随手核对那一行的实际内容（`if len(row) < 0:` 赫然在目），而不是靠脚本自己的输出。

约定：

1. 反向验证脚本启动时**先按“原始副本”还原一遍，再取基线**：第一次运行时把每个目标文件复制到临时备份目录，之后每次运行都先还原。这样“被杀掉”“上次没还原干净”都不会污染基准。
2. **还原一律 `read_bytes()` / `write_bytes()`**（§3.11），并在每处还原后核对 SHA256。
3. 目标用例一旦可能弹出真实模态对话框，脚本要设超时并把「超时」也算成“行为确实变了”的证据；否则脚本自己会挂死，连带留下未还原的改动。
4. 锚点匹配要容忍仓库里不统一的换行：本仓库 `winui.py`、`folders.py`、`app.js` 与几个 manifest 是 **CRLF**，其余是 LF（见 §3.13）。做锚点匹配时按文件自己的换行风格对齐，别假设 LF。

### 3.13 换行并不统一，暂时不要顺手统一（2026-09-26 记录）

按字节核对时发现 19 个文本文件含 CRLF：

| 文件 | 说明 |
| --- | --- |
| `build/mdreader/winui.py`、`folders.py`、`tests/test_folders.py` | 手写代码，某个会话的编辑留成了 CRLF |
| `build/webui/app.js` | 网页脚本 |
| `plugins/official/*/manifest.json`、`build/mdreader/plugin_trust.json` | **由脚本生成**：Python 文本模式写盘在 Windows 上会把 `\n` 翻成 `\r\n` |
| `docs/*.md`、`build/启动 MDReader.bat` | 文档与批处理 |

本轮**没有统一**，原因是 manifest 位于已发布的插件包内：改它的字节就会改变 `1.0.1` 的包哈希，而受信清单只认当前登记的哈希，等于必须同时升版本、重打包、重登记、重装——那是一件应该和版本号一起做的事，不是顺手清理。约定：下一次升版本号时统一为 LF（含生成器显式 `newline="\n"`），并在同一次交付里重建插件包与受信清单。

**2026-09-26 补充（同一教训的第二次）**：批量改写文件时不要用 `[IO.File]::WriteAllLines` / `Set-Content` 直接落盘——它们在 Windows 上按 `\r\n` 写整份文件。F03 补交付时用它改 `tests/editor.test.cjs`（本来是 LF）里的一处标识符，结果整份文件变成 CRLF；发现后立刻按**字节**把 `0D 0A` 还原成 `0A`（不做编码往返，避免中文再被转一次）。以后改文件先考虑 `edit` 工具（它保持原有换行），确实要批量处理就显式写 `LF` 字节。改完随手数一下 `CRLF/LF`。

### 3.14 验收记录不是可以顺手清理的文件（2026-09-26 的教训）

`scripts/acceptance.py --write` 按**日期**命名记录（`docs/acceptance-<版本>-<日期>.md`），所以同一天多次运行会**覆盖**同一份文件——这是有意的：一天之内只留最后一份结论。但由此带来两条约束：

1. **清理命令不要和验收/发布命令混在同一条命令行里**。本轮把 `Remove-Item docs\acceptance-...-2026-09-25.md` 与两次 `--write` 写在了一起，结果误删了上一轮的源码记录，而 `Remove-Item` 不进回收站（已确认无法恢复）。要清理什么，单独一条命令、单独确认一次再执行。
2. **删掉的旧记录不要“补造”**。那一轮的数字是在当时的代码上跑出来的；用新代码重跑一遍再改成旧文件名，就是把历史记录伪造成当前结果。正确做法是**如实记录这次损失**（在 `NEXT_AUTHORING.md`、`ROADMAP.md`、`acceptance-manual-notes.md` 写明哪份文件没了、为什么、数字还能从哪里查到），并保留其余引用。

另外记住：`docs/acceptance-*.md` 里**嵌着当时的 `acceptance-manual-notes.md`**。手工条目改完之后要重跑对应矩阵（`--write`）让记录与说明同步，否则记录里的“仍需人工确认”会和说明文件对不上。

### 3.15 反向验证前必须清掉字节码缓存（2026-09-26 的教训）

反向验证的突变往往**只有一两个字符的差别**（`"error"` → `"warn"`、`if x:` → `if False and x:` 之外的等长改动）。如果这次改动与上一次编译 `.pyc` 落在**同一秒**、且文件**大小不变**，CPython 的缓存校验（源文件 mtime + 大小）就会认为缓存仍然有效——测试跑的还是旧代码，表现为「这个突变没被任何用例抓到」。

本轮实测到了：F06 的七条突变里有两条一度报「未被测到」，手工改一处再跑同一个用例却立刻失败。结论与约定：

1. 反向验证脚本在**每次**运行目标用例前清掉 `build/**/__pycache__`（本轮之后所有该类脚本都这么做）。
2. 见到「MISS」先怀疑两件事：**突变到底有没有进到被测代码里**（打印那一行、或手工复现一次），以及**目标用例是不是真的覆盖了这条分支**。前者是脚本问题，后者才是测试盲区——两者的处理完全不同。
3. 突变脚本里的「目标用例清单」要跟着用例改名一起改：本轮就出现过一条突变的 targets 被误指向另一个用例，于是它“当然”测不出来。



先跑一遍能自动判定的部分，它会在真实窗口和临时工作区上按验收矩阵逐行检查并打印结果：

### 4.1 验收脚本自身的失败处理（0.2.8 教训）

E01 开发中，验收矩阵在「【编辑】」小节连报失败并一度卡住多个来回，**根因是脚本自己错了，不是产品缺陷**：新小节直接取 `win.tabs[0]`，而前面的小节留下了标签（其中一份项目文档还被故意制造过外部修改冲突），于是「保存」落到了那份文档上，脚本却去核对另一个磁盘文件；相关的 `save_doc` 冲突分支还会弹出模态对话框，表现为“卡住”。记录如下约定，避免重复浪费：

1. **每个小节先建立自己的前提**：进入小节时关掉遗留标签（`with _quiet_prompt(win)` 包住 `close_tab`），需要哪份文档就按 `_tab_key` 精确选中，不要用 `tabs[0]`/`tabs[1]` 这类位置下标。
2. **脚本里手工构造的状态要一次写全**：例如把草稿指向磁盘上尚不存在的目标时，必须同时把 `revision` 置为 `missing`，否则保存会被判定为外部修改冲突并弹窗。
3. **先判断是脚本还是产品**：失败先看脚本断言的目标是否就是它准备的那份文档；确认是脚本问题时改脚本，不要为了让断言通过而放宽产品判定。产品行为以 `tests/` 里的窗口级用例为准。
4. **不要悬在同一个失败项上**：同一小节排查超过约两轮（一次复现 + 一次定位）仍未收敛时，先把该项按 `SKIP` 记录原因并继续跑完矩阵，再单独处理；不允许为了让它变绿而伪造通过。模态对话框会阻塞自动化，排查挂起时先看日志末行停在哪一句、并确认没有遗留 `python` 进程。
5. **超时兜底**：脚本排查期间给命令设显式超时；矩阵运行应保持在数十秒内（0.2.8 实测 12–20 秒、通过 68、失败 0、跳过 4），明显变长通常意味着弹了对话框或在等资源，而不是用例本身慢。
6. **界面状态要“等到稳定”，不能只采一帧**（P01 的记录）：真实开窗的检查项如果只采样一次，就可能正好落在两个合法状态之间。安装副本生命周期里的「标题显示版本」在同一个构建上**一次失败、一次通过**：Tk 先映射窗口、再设置标题，采样恰好读到映射后、设标题前的那一帧。该项现在会轮询到标题稳定（最多 10 秒）再判定。给界面写断言时先问一句：这个状态是最终状态，还是会再变一次？
7. **脚本不要吞掉自己的命令行参数**（F09 的记录）：`scripts/acceptance_matrix.py` 需要在导入 `acceptance` **之前**把 `--root` 摆进 `sys.argv`（那个模块在导入时按它决定被测代码根目录），第一版直接截断了 `sys.argv`，于是 `--write --label installed` 被一起丢掉——跑完只打印结果、没写记录，看起来“一切正常”。现在把原始参数另存一份给 `argparse` 用，只把 `--root` 交给被导入的模块。给脚本加参数时记住：**先确认记录真的写出来了**，别只看退出码。
8. **不要用真实系统对话框做自动断言**：A03 一开始想验“真实回收站”，`SHFileOperation` 弹出系统确认框把无人值守的运行挂死（超时才被发现）；`delete_folder_doc` 在标签位于前台时还会走 `askyesnocancel` 的三选一。结论：这类分支一律在脚本里显式应答（`messagebox` 的 mock）或模拟（把文件挪到“模拟回收站”目录），真实回收站的可恢复性留给人工。**给任何新写的自动用例提个醒**：先看这条路径上有没有模态框，再决定能不能无人值守地跑。

然后按矩阵人工确认：

- 中文和空格路径：创建项目、新建文档、编辑保存、重启再读。
- 长文、表格、代码、图片、明暗主题和窗口缩放。
- 未保存时切换文档/项目：保存、放弃、取消三条分支；保存失败内容仍在。
- 导入目录结构，导出单篇/合集后断网打开。
- 回收站删除与恢复、文件被外部编辑器修改后的行为。

#### F01 已落地的两条工程约定（2026-09-25）

- **可见性探测必须看文件，不能只看目录**：Windows 上修改文件内容**不会**更新父目录的 mtime，只比较目录时间戳会漏掉“深层子目录里的文件被改了”。`folders.py::_deep_signature` 因此同时采集目录与 Markdown 文件的 mtime/大小，并设了上限；轮询线程再按间隔决定要不要真正全量走目录（1000 份 MD 的全量扫描 47 ms、无变化的一眼 0 ms，本机 SSD）。

#### F05 小样验证结论：公式怎么画（2026-09-26）

任务书要求“先做小样验证”再定方案，下面是**实测**结果与选择理由。

候选与实测：

| 候选 | 实测 | 结论 |
| --- | --- | --- |
| KaTeX 本地资源 | 本机可访问 npm registry 与 jsdelivr（HTTP 200）；脚本+样式+字体约 1.5 MB | 能用，但**桌面预览是 Tk**（只能放图片），PDF/DOCX 插件也没有浏览器可用，四条出口里只有两条能直接用它 |
| 现成 Python 转换器 | 开发机有 `matplotlib`，但**不随程序分发**；`latex2mathml`/`sympy` 未安装 | 会让核心多一个几十 MB 的依赖 |
| Windows GDI + 自写 PNG | 小样通过：文字画进位图并扫描像素可量可画；自编码的 PNG 能被 Tk `PhotoImage` 直接读 | **采用** |

选择「GDI 渲染成 PNG、按内容缓存」的理由：桌面预览（Tk `Text` 的 `image_create`）、网页与
自包含 HTML 导出、PDF/DOCX 嵌入**都通向同一张位图**；一套渲染器只有一套结果要验证，也不必
为了 HTML 自包含去内联 1.5 MB 资源。代价如实写在已知限制里：不支持可变长括号、数学间距与
断行的细节不如 KaTeX，只承诺样本表里的语法。

小样里踩到并解决的四个坑（都写成了注释，防止以后“优化”掉）：

1. **`GetGlyphOutlineW` 在本机对所有字体都返回 `GDI_ERROR`**（`GetGlyphIndicesW` 与
   `GetCharABCWidthsW` 正常）。所以字形的上下伸改成：先用 `GetGlyphIndicesW`（带
   `GGI_MARK_NONEXISTING_GLYPHS`）判断字体里有没有这个字形，再把字符画在白底探针位图上
   **扫描像素**量出墨迹范围。不能只靠像素判断“有没有字形”——GDI 对缺字形会画一个空框。
2. **`FIXED` 结构的字段顺序是 `fract` 在前、`value` 在后**，写反了 `MAT2` 就成了退化矩阵，
   `GetGlyphOutline` 一律失败。
3. **Cambria Math 的行高是字号的 5 倍多**（20 px 的字号 `tmHeight=111`，`tmAscent=62`），
   按行高排版会得到一堆空白。度量必须用**墨迹框**，不能用 `TEXTMETRIC`。
4. **`\\` 必须在 `\命令` 之前匹配**：正则 `\\([A-Za-z]+|.)` 会把 `\\` 的第一个反斜杠当成
   命令、第二个当成参数，于是矩阵与 `aligned` 的行分隔符从来没生效过（表现为所有行挤成一行）。

验收锚点：`tests/test_formula.py`（识别、语法、产物、缓存四组 31 项），其中样本表
`formula.SUPPORTED_SAMPLES` 同时是**承诺的支持范围**，用例、验收矩阵与用户说明都引用它。

#### F03 图片插入三条入口的工程约定（2026-09-26）

- **读剪贴板必须由用户动作触发**：`media.clipboard_image()` 只在菜单项/`Ctrl+Shift+V` 被按下时调用，程序不装剪贴板监听、不保留历史。用例断言「插件没启用时连读都不读」——这一条比“读到了但没插”更容易被以后的改动破坏。
- **`CF_DIB` 没有文件头**：剪贴板里的 `CF_DIB` 是 `BITMAPINFOHEADER` +（调色板）+ 像素，**不是** `.bmp` 文件；像素起点是 `size`（信息头长度）而不是 `size + 14`。算错的表现是图像整体错位、并在“数据长度不够”上被当成坏数据拒绝——隐藏得很好，所以做成逐像素核对的用例。
- **自写 PNG 编码器要能被独立解码验证**：`_clipboard_png_from_dib()` 只输出 8 位 RGB、每行过滤器 0。验收脚本用 zlib **重新解一遍**再比对像素（`_png_rows()`），不接受“编码器自己说对了”。
- **清理前先判断归属**：剪贴板给的路径有两种来源——我们自己 `mkstemp` 出来的临时文件，和用户在资源管理器里“复制”的原件。`owns_clipboard_file()` 用「在系统临时目录里 + `clipboard-` 前缀」两个条件判定，只有为真才 `os.remove`。反向验证里把这条改成 `return True`，“用户原图必须还在”的用例立刻失败。
- **三条入口共用一条通道**：文件选择、剪贴板、拖放都调 `winui.insert_image_file()` / `webui.insertImageBlob()`，插件只负责转换、宿主负责落附件与提交正文。新增入口时不要再写第二套“落盘 + 写正文”，否则撤销粒度、修订校验和失败清理会各自走样。
- **拖放按类型分流、并说清“只处理了一张”**：图片 → 插入当前文档；`.md` → 临时打开；文件夹 → 导入。一次拖入多张只插第一张并提示其余数量——不静默丢弃，也不连环弹窗。
- **下限保护要如实暴露**：图片宽度 16–4096 是插件的既有保护，宽度小于 16 px 的图会得到插件的报错而不是被悄悄放大。验收底图要选在门槛之上，否则验的是门槛而不是链路。

#### F06 已落地的工程约定（2026-09-26）

- **导出的公共部分只在核心，插件只转格式**：`mdreader/exporting.py` 决定“导出哪一份内容、有没有问题、写到哪”，并通过 `POST /api/export/check`（只算不写）与 `POST /api/plugins/export`（三道拦截后执行）暴露给两端。桌面与网页调的是同一份实现，所以阻止条件与提示文字只有一套。
- **未保存必须让用户选**：缓冲区与磁盘不一致时，导出前先问「当前编辑内容（推荐）」还是「磁盘已保存版本」；用户不选就不写文件。**已经保存过的文档不问**，避免每一步都弹框。
- **严重问题与可降级项分开**：缺图、越界图、空文档 → **阻止导出**；写不出来的公式、过宽表格、失效本地链接、字体缺失、超大文档 → 提示并等确认。任何一项都要给出**原因文本**，不能只说“导出失败”。
- **预检只算不写**：预检与来源选择不得创建目录、写缓存或改源文（有用例断言目录列表不变）；导出本身仍是“目标同目录临时文件 → 校验 → 原子替换”，失败或取消保留原目标。
- **图片与链接共用同一个授权读取器**：`Api._resource_reader` 把相对路径解析成授权范围内的真实路径，越界一律 `PermissionError`。预检里**“读不到”与“文件不存在”要分开报**（本轮就是因为把 `NameError` 混进“找不到图片”，让一个代码错误伪装成了用户数据问题）。
- **插件任务借事件循环时不要弹模态框**：`media_ui.run_job` 用 `wait_variable` 让界面在等待插件时继续重绘，这段时间里定时器弹出的模态框会把任务和用户一起卡住。凡是“定时器里主动弹窗”的功能（恢复快照、自动提示）都要先看 `self._plugin_busy`，忙就把自己往后挪。



#### F05 已落地的工程约定（2026-09-26）

- **公式是图片，所以主题必须进缓存键**：PNG 里带着画好的前景/背景色，CSS 变量换不掉它。缓存键 = 表达式 + 字号 + 缩放 + 主题 + 粗细 + **渲染器版本**；网页端切换主题时只重指 `<img>` 的 `src`，不重排正文（也就不会丢阅读位置）。
- **先换哨兵、再替换回来**：`render_markdown` 先把公式换成哨兵（正文照旧过内容白名单），渲染完再替换成图片标签。这样正文里的 `$` 与代码块里的 `$` 由 markdown 规则区分，公式 HTML 走一条**只由我们自己生成**的通道——不能因为“支持公式”就放行文档里的脚本（用例里正文的 `<script>` 仍然被转义）。在渲染后的整页 HTML 上做全局正则替换是明确不做的。
- **画不出来就显示源码**：解析失败、命令不支持、超限，一律 `<span class="formula-error" title="原因">原始表达式</span>`（转义后输出），正文其余部分照常渲染。桌面预览同理：失败时把 `$…$` 原样留在正文里。
- **桌面预览不需要 PIL**：Tk 8.6 自己就能读 PNG（缓存文件直接给 `PhotoImage(file=…)`，内存里的图用 base64 给 `PhotoImage(data=…)`），所以公式这条路径没有引入新的运行期依赖。
- **未闭合的 `$$` 按普通正文处理**：块级解析找不到结尾时必须退回普通段落，否则一次笔误就会把后面整篇文档吞进“公式”里（用例锁住这条）。
- **缓存写不进去也要能看**：`formula.cached()` 在目录不可写/磁盘满时返回内存里那张图（`path=""`），桌面端与网页端都不会因此丢公式。

#### P01 已落地的工程约定（2026-09-25）

- **发现阶段绝不导入插件代码**：`plugins.PluginStore` 只读 `manifest.json`，命令与格式全部来自校验过的清单字段（未列出的键一律拒绝，包括 `html`/`script` 这类界面代码字段）。真正执行才由 `plugin_tasks.TaskManager` 起一个独立进程；`mdreader.plugin_worker` 是那个进程的唯一入口，插件拿不到 Tk 控件、网页 DOM、可变文档对象或核心服务对象。用例在启用插件后断言 `sys.modules` 里没有任何 `mdreader_plugin_*`，把“惰性”钉成结构。
- **协议只有四种消息**：宿主向工作进程的标准输入写一个 JSON 对象后关闭输入；工作进程在标准输出上只写 `progress` / `result` / `error` / `log` 四种 JSON Lines。插件自己的 `print` 被重定向到标准错误，避免污染协议通道。任务带 `task/api_version/plugin/entrypoint/capability/method/workdir/document/options/input/format`，其中 `document` 记录调用时的文档身份、修订与入口。
- **结果一律由宿主复核**：产物必须落在任务工作目录内（`os.path.realpath` + `is_within`），导出还要比对清单声明的扩展名、文件头 `magic` 与 `max_bytes`；图片要过文件头白名单。提交前再比一次文档修订，不一致就抛 `StaleResult`；被取消、超时或禁用过的任务，结果永远不可采用。
- **受信清单不能由用户目录决定**：只有随程序分发的 `mdreader/plugin_trust.json` 里登记了该 id 与包 SHA256 的包才能安装；清单自称官方、包内自带哈希都不算证据。测试与本地开发通过构造参数注入临时清单，界面**不提供**“忽略来源检查”的开关（只有服务端接口的显式 `allow_unverified`）。打包是确定性的（成员排序、时间戳固定），所以哈希可复现。
- **状态一处保存、两端共读**：启用状态写在应用工作区 `plugins.json`，`PluginStore` 按文件 mtime 重新加载，桌面窗口与网页直接读同一份，因此不需要重启就一致；禁用会先取消该插件正在跑的任务，服务端随后拒绝失效命令（隐藏按钮不是权限控制）。
- **禁用/卸载的清理边界**：卸载只删 `plugins/installed/<id>` 与 `plugins/cache/<id>`，动手前用 `is_within(plugins_dir, …)` 复核；文件被占用时不强删，改为“已禁用 + 重启后生效”。用户文档、已插入图片与已导出文件不在任何删除路径上。
- **测试真的起工作进程**：`tests/test_plugins.py` 用 `plugins/samples/*` 现场打包的样例插件跑真实子进程（正常、异常、超时、取消、越界结果、坏文件头、运行中禁用），因此该模块耗时明显高于其他模块——这是“独立进程执行”的直接代价，不应为了跑得快改成同进程调用。样例插件**不是产品**：样例导出格式的扩展名是 `.samplea/.sampleb`，不冒充 PDF/Word；正式三个包在 `plugins/packages/`，哈希登记在随程序分发的受信清单里。

#### 三个正式插件的工程约定（2026-09-25）

- **字形覆盖率必须逐字符判断，不能假定“字体有这个字”**：中文正文/标题字体（SimSun、黑体、微软雅黑）都没有数学减号 `U+2212` 与上下标 `U+2076 ⁻`、`U+2081 ₁`。ReportLab 遇到没有字形的字符**不报错**，照画一个空的 `.notdef`——导出稿上就是一块空白（维护者试用时反馈的「转换后出现乱码」）。`plugins/official/common/exporting.py` 现在自己解析字体 `cmap`（只认 Unicode 子表，支持 format 0/4/6/12，`.ttc` 取第 0 个字面），按字符在基础字体 → Times New Roman → Cambria → Segoe UI Symbol 之间挑字体；Word 侧用同一套判断拆 run 并显式写出 `w:ascii`/`w:eastAsia`。控制字符（换行、制表）不算缺字形。
- **两个插件必须共用同一套判断**：DOCX 插件不装 ReportLab，所以判断不能依赖 ReportLab 的 `charToGlyph`。自写解析器用 fontTools 作为独立实现逐个码点核对（`tests/test_official_plugins.py`），并把“只认 Unicode 子表”这条钉死——把 Mac Roman 子表也算进来会凭空多出几十个控制字符的“字形”。
- **连回退字体也没有字形时不假装成功**：导出仍然完成，但结果里带一条提示（列出受影响的字符），桌面端显示「（N 条提示）」。这条不能改成“静默留空”，否则用户看到的就是没有解释的空白。
- **正式包的版本与哈希**：`scripts/build_official_plugins.py` 是确定性打包（同一份源码永远得到同一个 SHA256），打包后直接把哈希写进 `build/mdreader/plugin_trust.json`；`scripts/install_official_plugins.py` 只在版本不同的时候安装（走真正的升级路径），`scripts/verify_official_plugins.py` 生成可供人工渲染检查的样本。旧版本的安装包要从 `plugins/packages/` 删掉：清单只认当前登记的哈希，留着旧包只会让“这个包能不能装”变得含糊。

#### F04 已落地的工程约定（2026-09-26）

- **内容规则只写一份，界面只负责收发**：表格识别/修改与格式动作都在 `mdreader/tables.py`、`mdreader/formatting.py`；桌面端直接 `import`，网页端走 `POST /api/edit/table`、`POST /api/edit/format`（服务端算完把新正文与新选区发回来）。这两类操作**不写磁盘**（用例断言调用前后工作区目录列表不变），所以让服务端参与网页编辑是安全的；反过来，任何“写文件”的动作仍然只走既有的授权服务。- **看不懂就拒绝，不猜**：`tables.review` 逐项核对表头、分隔行、列数、各行首尾竖线、单元格两侧空白，任何一项对不上就返回原因，界面保留源码并提示；围栏代码块里的伪表格不算表格。反向验证的第一项就是它：去掉列数核对后两个用例立刻失败。
- **一次操作一次撤销**：桌面端写回用一次 `editor.replace(...)`（Tk 记成一个撤销单元）并临时关闭 `autoseparators`，结束时恢复；写成「先删后插」会被自动分隔切成两组，撤销只回退一半（正文少了字、插入的标记还在）。网页端写回 `value` 后**派发一次 `input`**，页面才会标记未保存。
- **转义要与渲染器一致**：单元格里的 `|` 写成 `\|`、`\` 写成 `\\`；行内代码的围栏长度按内容里最长的反引号串决定，必要时补空格——两条都用 markdown-it 交叉验证（转义后的文本渲染回来必须等于原文），而不是自己另定一套。
- **粘贴先看清楚**：多行多列的剪贴板文本先给「几列几行 + 不能原样处理的地方」预览，确认后才写入；取消与普通粘贴完全不拦。列数不一致时**补空单元格并警告**，绝不静默错列。
- **宽表不裁列**：阅读界面的每列最小宽度随窗口收窄（宁可单元格里多换行），验收断言 12 列 × 2 行 = 24 个标签都在且每列都能换行；导出侧 PDF 逐列核对文本层、Word 逐行核对单元格数。多出表头列数的单元格按 GFM 规则裁掉，**阅读端与导出端用同一个解释**（有用例钉住）。
- **弹层不替用户“猜”超出范围的内容**：超过 60 行 / 16 列的表不进表格弹层（保留源码并提示），因为弹层提交的是整张表——只显示一部分再提交，等于删掉没显示出来的行列。
